# klar 3.0 — agreed design

**Status: reviewed and agreed. Implementation spec, not yet built.**

This is the end state of the work coming out of [#9], after a section-by-section
review. It supersedes the proposal that preceded it; the open questions are
resolved and recorded in §9 with what would change our minds.

Once the code lands, this folds into `README.md` (command reference) and
`AGENT_PLAYBOOK.md` (agent guidance), and this file is deleted. It exists only
because the shipped docs should not describe features that don't exist yet.

Outputs marked *(illustrative)* are projected. Everything else is a measured
value from the current branch.

## 2. Gamut mapping

A color that can't be shown has to become *something* before it can be measured.
klar resolves that with **CSS Color 4 gamut mapping** — chroma reduction until
the color fits — everywhere it maps a color, whether measuring or producing.

klar takes no position on what any particular browser does. Anticipating engine
behavior means maintaining a matrix of engines and versions forever, and losing.
The spec is a stable reference; implementations aren't.

```
--gamut-map <method>       clip | css | none        (default: css)
```

| Method | Behavior | Use when |
|---|---|---|
| `css` *(default)* | CSS Color 4 chroma reduction | Always, unless you have a specific reason |
| `clip` | Clamp each channel into range | You need this specific, well-defined operation |
| `none` | Measure the authored color, unmapped | You want colorimetry, not a displayable color |

`--gamut-map` exists on **`contrast` only**. On commands that *produce* colors —
`find`, `match` — every place the flag could apply is either structural (the
normalization has to happen or there's no renderable output) or a no-op
(candidates are in-gamut by construction, where mapping does nothing). Producing
commands always use the standard mapping.

`KLAR_GAMUT_MAP` sets the default process-wide, matching the existing
`KLAR_PLUGINS` / `KLAR_NO_PLUGINS` convention. It's the migration path for a team
with a large token set: pin the old behavior, upgrade, unpin deliberately.

> **There is no `--gamut <space>` flag.** Wide-gamut support is deferred (§8), and
> a flag with one legal value can't change any behavior. When a second space
> exists, `--gamut p3` is purely additive — no collision, no rename, because
> `--gamut-map` already owns the method namespace.

### The invariant

**Environment can change what klar measures against. Nothing in the environment
can silence a signal.** `KLAR_GAMUT_MAP` is configuration and should be uniform
across a project. Waiving a failure is a per-call judgment made where someone can
see what they're waiving. So every mapping mode still reports `outOfGamut` and
still exits 1, and no combination of env settings produces a quiet mapped
measurement.

### One consequence worth knowing

Chroma reduction maps **every** out-of-gamut chroma at a given lightness and hue
onto the same boundary color:

```
oklch(0.79 0.22 25)   out of gamut   →  #ff938b  →  6.1
oklch(0.79 0.15 25)   out of gamut   →  #ff938b  →  6.1     ← identical
oklch(0.79 0.12 25)   in gamut       →  #fe9b93  →  6.9
oklch(0.79 0.10 25)   in gamut       →  #f4a19a  →  7.5
```

Measured contrast is **flat across the entire out-of-gamut range**, then starts
moving once the color is inside. Two genuinely different authored tokens produce
an identical number, so the out-of-gamut signal is the only thing distinguishing
them in output. That is why it can never be trimmed for token cost.

## 3. `contrast`

```
klar contrast <foreground> <background> [options]
```

| Flag | Default | Description |
|---|---|---|
| `-t, --type <type>` | `okca` | `okca`, `wcag2`, `deltaE`, plus installed plugins |
| `--gamut-map <method>` | `css` | Out-of-gamut resolution |
| `--allow-out-of-gamut` | off | Exit 0 instead of 1 when an input is out of gamut |
| `--json` | | JSON output |
| `-q, --quiet` | | Bare numeric value |

### Exit codes

| Case | Exit |
|---|---|
| Both inputs in gamut | 0 |
| An input is out of gamut | **1** |
| An input is out of gamut, `--allow-out-of-gamut` | 0 |
| `--gamut-map none --type okca` | 2 |
| Unparseable color, bad args | 2 |

Exit 1 is a soft failure by the existing contract's own definition: a valid
operation whose answer is negative. The measurement is of a color that isn't the
one you authored, so the number goes to stdout for inspection while the exit code
stops it being silently adopted — the same mechanism that already protects `find`.

`contrast` needs no `reason` field. Exit 1 has exactly one meaning, and
`gamut.outOfGamut` is already its machine-readable form.

There is deliberately **no environment variable** for `--allow-out-of-gamut`. A
global mute is set once in CI and never removed, which reinstates precisely the
silent-failure mode this release exists to eliminate.

### `-q` and stderr

`-q` stays a bare number — that's its entire value, and anything else breaks
`$(…)` composition. Between the float on stdout and the exit code, an agent gets
both the value and whether to trust it. stderr adds *which* color, without
forcing a second call in `--json`:

```
klar: oklch(0.79 0.22 25) is outside srgb; measured as #ff938b
```

Fires only on out-of-gamut input.

### `--json`

In gamut — the common case — costs three lines:

```jsonc
{
  "contrast": 20.9,
  "type": "okca",
  "colorOne": "#ffffff",
  "colorTwo": "#000000",
  "gamut": { "map": "css", "outOfGamut": false }
}
```

Out of gamut adds `measured`, listing only the colors actually mapped:

```jsonc
{
  "contrast": 6.1,
  "type": "okca",
  "colorOne": "oklch(0.79 0.22 25)",
  "colorTwo": "#070e16",
  "gamut": {
    "map": "css",
    "outOfGamut": true,
    "measured": { "colorOne": "#ff938b" }
  }
}
```

### Refusal

`--gamut-map none` with `--type okca` exits 2:

```
Error: --gamut-map none cannot be used with --type okca.
OKCA's guarantee is established across the sRGB gamut; outside it the
result is unvalidated extrapolation. Use --gamut-map css or clip, or
--type wcag2 / deltaE, which are defined continuously.
```

The shipped build gives a *representation* reason ("hex cannot represent…"),
which is wrong — okca accepts `oklch()` strings directly. The real limit is the
algorithm's **validity domain**, which is also the limit that matters for wider
gamuts later.

## 4. `find`

```
klar find <base-color> <reference-color> --target <n> [options]
```

| Flag | Default | Description |
|---|---|---|
| `--target <n>` | *(required)* | Target contrast |
| `-t, --type <type>` | `okca` | Algorithm |
| `--tolerance <n>` | `0.5` | Acceptable overshoot above target |
| `--allow-desaturation` | off | Permit reducing chroma to reach the target |
| `--json` / `-q, --quiet` | | Output mode |

### Two chroma operations, only one optional

This distinction is the whole design.

**Gamut normalization is mandatory.** If the reference color is outside sRGB, it
is chroma-reduced onto the gamut boundary before anything else happens. Without
this there is no renderable color to return at all — it is the difference between
an answer and nothing. It is not governed by any flag.

**Target-reaching desaturation is optional and off by default.** Once the color
is in gamut, `find` searches lightness. If lightness is exhausted, it stops.
Trading brand saturation for contrast is a design decision, not a computation,
and an agent silently accepting a desaturated brand color produces drift that no
single call reveals.

Issue [#9]'s own case is solved by the mandatory half alone:
`oklch(0.79 0.22 25)` at `--target 6` normalizes to the boundary color at 6.1,
which meets the target. Exit 0, no discretionary desaturation.

Colors already in gamut are unaffected — normalization is a no-op and the
lightness search proceeds exactly as today.

### Escalation instead of silent substitution

When lightness is exhausted, `find` exits 1 — but reports what *would* solve it
without applying it:

```jsonc
// (illustrative)
{
  "adjustedColor": "#ff938b",
  "actualContrast": 6.1,
  "success": false,
  "reason": "lightness-exhausted",
  "resolvableBy": { "chroma": 0.10, "deltaE": 12 },
  "axesAdjusted": ["lightness"],
  "oklch": { "l": 0.79, "c": 0.17, "h": 25 },
  "gamut": { "outOfGamut": true, "measured": "#ff938b" }
}
```

That turns a dead end into an informed escalation: a creative lead learns a
solution exists and exactly what it costs, and the agent can't take it
unilaterally because klar didn't apply it. `--allow-desaturation` is the record
of a human having made that call.

### Exit codes

| Case | Exit | `reason` |
|---|---|---|
| Target met | 0 | `ok` |
| Target met after mandatory gamut normalization | **0** | `ok` |
| Lightness exhausted | 1 | `lightness-exhausted` |
| Chroma reduced to 0 and still short (`--allow-desaturation`) | 1 | `unreachable` |
| Unparseable color, bad args | 2 | — |

Row 2 is the behavioral change: an out-of-gamut reference currently exits 1 with
the input handed back untouched, and becomes exit 0 with a solved color.

Two contract improvements come free:

- **The exit-1 payload is always renderable.** Gamut normalization runs first, so
  "returns the input unchanged" is structurally impossible. Exit 1 upgrades from
  "here's something, possibly your own input back" to "here's a usable color, as
  close as this constraint allows."
- **`reason` describes the caller's constraint, not klar's limitation.**
  `lightness-exhausted` means *you* declined desaturation. `unreachable` — only
  possible with `--allow-desaturation` — means no color reaches the target
  against this base, since the search reaches chroma 0 where hue is moot.

### Payload fields

`axesAdjusted` reports what moved **to reach the target**. Gamut normalization is
reported separately under `gamut`, never as an axis — otherwise the default
configuration would confusingly report `["chroma"]`.

`deltaE` is perceptual drift from the reference color. The playbook currently
teaches a separate `klar contrast --type deltaE` call to measure it; folding it in
saves an invocation per token.

### stderr

An out-of-gamut reference produces a note at **exit 0**, because normalization
happening invisibly to a `-q` caller would itself be a silent substitution:

```
klar: reference oklch(0.79 0.22 25) is outside srgb; normalized to #ff938b
```

## 5. `lightness` and `variants`

No new flags. One bug fix and one signal.

### `lightness` reports a false range when nothing is in gamut

```bash
klar lightness "oklch(0.5 0.9 25)" --json
# { "lightMin": 0.5, "lightMax": 0.5 }        exit 0
```

Chroma 0.9 is renderable at no lightness whatsoever, but the output reads as "the
usable range is exactly 0.5" — a single valid point. It comes from the fallback in
`getMinMaxLight` (`color-util.service.ts:98`), which returns the input's own
coordinates as both bounds when no variant survives the gamut filter. An agent
asking "what lightness can I use?" gets a confident, specific, false answer.

Same shape as the other two defects in this release: a plausible value, no signal,
error running in the permissive direction.

**Fix:** empty range → **exit 1**, null bounds, payload still written.

The format already expresses the honest answer in the non-degenerate case —
`oklch(0.45 0.22 25)` correctly returns `0.543–0.667`, a range that *excludes* the
input's own lightness. Only the empty case fails.

### Neither command signals out-of-gamut input

Both gain `gamut.outOfGamut` in `--json`. Today `variants` silently walks chroma
from 0.4 down to 0.035 to find renderable cells and says nothing about it.

Neither exits 1 merely for out-of-gamut input — both still produce a useful
answer, so they follow `find`'s side of the split rather than `contrast`'s.

## 6. okca at full precision

okca currently receives hex, which quantizes to 8 bits, while `wcag2` and `deltaE`
work continuously — so the algorithms disagree slightly about what color they are
measuring. Rather than quantizing the continuous ones *down* to match, route okca
through `oklch()` strings and close the gap *upward*.

okca accepts `oklch()` directly, and agrees exactly with the hex route on
chromatic colors:

```
#ff746f   hex: 4     oklch: 4
#3b82f6   hex: 2.2   oklch: 2.2
#e94560   hex: 2.3   oklch: 2.3
```

This also drops an sRGB-shaped bottleneck out of the architecture, since `oklch()`
carries wide-gamut coordinates fine.

> **Landmine — must be handled.** Achromatic colors convert to a `NaN` hue, and
> okca rejects them:
>
> ```
> #767676  →  oklch(0.5658 6.2e-16 NaN)  →  null
> ```
>
> Normalize hue to `0` before serializing, or every neutral gray in a design
> system returns "unable to calculate contrast." Pin with a test.

Three colors is not verification; a proper sweep runs before this lands.

## 7. Playbook guidance

Additions to `AGENT_PLAYBOOK.md`.

### Exit codes are the primary signal

The playbook has no consolidated exit-code table today. It needs one, because exit
codes now carry the out-of-gamut fact.

| Code | Meaning | What to do |
|---|---|---|
| 0 | Success; the value describes the color you asked about | Proceed |
| 1 | Soft failure — a valid operation with a negative answer | Read `reason` / `gamut`; do not adopt the value blindly |
| 2 | Usage error, or klar declined to answer | Fix the call; don't retry with different flags to make it go away |

### Gate vs. audit

| Job | Mode | Why |
|---|---|---|
| **Gate** — "does this pass?" | `-q` + `$?` | The float answers it; the exit code says whether to trust the float |
| **Audit** — "why, and what do I do?" | `--json` | You need `reason`, `resolvableBy`, `gamut.measured` |

Every byte of output is a token, paid on every call. `-q` carries more than it
looks like it does — reach for `--json` when you need *which* color and *what it
became*, not by default.

### A mapped measurement is not a measurement of what you authored

When a color falls outside the gamut, klar maps it to the nearest displayable
equivalent and measures that. The number is real, but it does not describe the
color in your token file.

Reducing chroma is the fix — but **the number will not move until the color is
actually in gamut**. Chroma reduction maps every out-of-gamut chroma at a given
lightness and hue onto the same boundary color, so `0.22 → 0.15` changes nothing.
Reduce until `outOfGamut` is false, and only then does further reduction help.

### Read `reason`, never `message`

```bash
RESULT=$(klar find "$BG" "$FG" --target 4.5 --json)
case "$(jq -r '.reason' <<<"$RESULT")" in
  ok)                    ;;   # done
  lightness-exhausted)        # a solution exists but costs saturation
    jq -r '.resolvableBy' <<<"$RESULT"   # escalate with the cost attached
    ;;
  unreachable)           ;;   # no color works against this base; change the base
esac
```

`message` is prose for humans and its wording is not stable.

### Don't resolve brand tradeoffs unilaterally

`reason: "lightness-exhausted"` with a `resolvableBy` block means a compliant
color exists, but only by desaturating — a brand decision. Report it with the
`deltaE` cost attached and let a human decide. `--allow-desaturation` exists for
pipelines where that decision has already been made.

## 8. Deferred

| Item | Why |
|---|---|
| `--gamut p3` / `rec2020` | **Blocked upstream.** okca's chroma weighting saturates above a threshold: `oklch(0.79 0.22 25)` and `oklch(0.79 0.45 25)` both score 5.9 against `#070e16`. Invisible inside sRGB, where the cap sits near the gamut boundary; in P3 it would flatten real differences into one number. Must be answered in okca first. |
| Plugin gamut declaration | `calculate(colorOne, colorTwo)` hands plugins two strings with no way to declare what they accept or where their algorithm is valid. Safe while everything is sRGB. Belongs in a plugin-interface major. |
| Bulk / multi-color audit | Real gap for large token sets; today developers script it. A genuine feature, not a rider on this one. |
| `--max-delta-e` bound on `find` | Arguably the better control than a boolean, since drift is what design teams actually care about. Deferred because `deltaE` in the payload lets callers apply that policy without klar inventing a threshold. |

To be filed as issues — one upstream against `pawn002/okca`, three against klar.

Not tracked: joint (L,C) optimization in `find`. Decided against on
predictability grounds — an agent has to justify the change it made, and
"reduced chroma to 0.10, the least that reaches 4.5" is explainable in a commit
message where an optimizer's pick isn't.

## 9. Provisional, and what would change it

The `find` default — escalate rather than desaturate — is the one decision that
can only really be judged by using it. Watch for:

- **`--allow-desaturation` passed on nearly every call.** The default is wrong;
  flip it.
- **`resolvableBy.deltaE` routinely below 3.** Imperceptible on the playbook's own
  scale, which means we're escalating decisions that don't matter. The likely
  revision is to auto-apply below a perceptibility threshold and escalate only
  above it. **Most probable outcome.**
- **Exit 1 plus `resolvableBy` routinely overridden without a human looking.**
  Escalation isn't functioning as a control, and the flag is theatre.

The design instruments itself: `resolvableBy.deltaE` in the payload produces
exactly the distribution needed to judge all three.
