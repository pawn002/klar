**Status: proposal for review. Not the shipped surface.**

This describes the *end state* of the work coming out of [#9], so the developer
and agent experience can be reviewed as a whole before it is built. Every item
is marked with its build status. Once this is agreed, it folds into
`README.md` (command reference) and `AGENT_PLAYBOOK.md` (agent guidance) and
this file goes away.

Outputs marked *(illustrative)* are projected, not measured. Everything else is
a real value from the current branch.

## 2. The two flags, and why there are two

This is the change most likely to feel like overhead, so it goes first.

A color that can't be shown has to become *something* before anyone sees it.
That involves two independent decisions:

- **Which gamut are we targeting?** — what the display can show.
- **How do we resolve a color outside it?** — the mapping method.

These are orthogonal. "Clip into sRGB" and "clip into P3" are the same method
against different spaces. Collapsing them into one flag works only while
exactly one space is supported, and stops working the moment a second one is.

```
-g, --gamut <space>        srgb                      (default: srgb)
    --gamut-map <method>   clip | css | none         (default: clip)
```

| `--gamut-map` | Behavior | Use when |
|---|---|---|
| `clip` *(default)* | Clamp each channel into the target space — what browsers paint today | You want the number a user experiences |
| `css` | CSS Color 4 gamut mapping (chroma reduction) | Reproducing a klar 2.x figure exactly |
| `none` | Measure the authored color, unmapped | You want colorimetry, not accessibility |

`--gamut` currently accepts only `srgb`. It exists now so that the flag which
selects a *space* is named for spaces from day one, rather than being retrofitted
over a flag that means something else. See §8 for why `p3` is not here yet.

`--gamut-map` applies only to commands that **measure** (`contrast`, `find`,
`match`). `--gamut` also applies to commands that **filter** (`lightness`,
`variants`), where the question is "which colors exist in this space" rather
than "what does this color become."

### Precedence

```
--flag  >  environment variable  >  default
```

`KLAR_GAMUT` and `KLAR_GAMUT_MAP` set the defaults process-wide, matching the
existing `KLAR_PLUGINS` / `KLAR_NO_PLUGINS` convention. This is the migration
path for a team with a large token set: pin the old behavior in CI, upgrade,
then unpin deliberately.

```bash
KLAR_GAMUT_MAP=css klar contrast "oklch(0.79 0.22 25)" "#070e16" -q   # 6.1 — 2.x figure
```

## 3. `contrast`

```
klar contrast <foreground> <background> [options]
```

| Flag | Default | Description |
|---|---|---|
| `-t, --type <type>` | `okca` | `okca`, `wcag2`, `deltaE`, plus installed plugins |
| `-g, --gamut <space>` | `srgb` | Target gamut |
| `--gamut-map <method>` | `clip` | Out-of-gamut resolution |
| `--json` | | JSON output |
| `-q, --quiet` | | Bare numeric value |

### Behavior

`contrast` reports the contrast of the colors **as an sRGB display paints
them**. A contrast figure for a color that cannot be displayed is not an
accessibility measurement.

```bash
klar contrast "oklch(0.79 0.22 25)" "#070e16" -q
# 4                      — measures #ff746f, what a browser paints

klar contrast "oklch(0.79 0.22 25)" "#070e16" -q --gamut-map css
# 6.1                    — the klar 2.x figure

klar contrast "oklch(0.79 0.22 25)" "#070e16" -q --gamut-map none --type wcag2
# 9.2                    — colorimetric value of the color as authored
```

### `-q` and stderr  ⬜ proposed

`-q` stays a bare number — that is its entire value, and anything else would
break `$(…)` composition. But a bare float has nowhere to put a caveat, so when
an input falls outside the target gamut, klar writes one line to **stderr**:

```
klar: oklch(0.79 0.22 25) is outside srgb; measured as painted (#ff746f)
```

stdout stays clean for piping. This follows the existing convention in
`utils/output.ts`, where soft-failure notes already go to stderr for the same
reason. It fires only on out-of-gamut input, which is rare and always
significant.

### `--json`  🔶 reshaping

In-gamut — the overwhelmingly common case — costs three lines:

```jsonc
{
  "contrast": 20.9,
  "type": "okca",
  "colorOne": "#ffffff",
  "colorTwo": "#000000",
  "gamut": { "space": "srgb", "map": "clip", "outOfGamut": false }
}
```

Out-of-gamut adds `measured`, listing only the colors that were actually
mapped:

```jsonc
{
  "contrast": 4,
  "type": "okca",
  "colorOne": "oklch(0.79 0.22 25)",
  "colorTwo": "#070e16",
  "gamut": {
    "space": "srgb",
    "map": "clip",
    "outOfGamut": true,
    "measured": { "colorOne": "#ff746f" }
  }
}
```

`gamut.outOfGamut` is the field to branch on. `gamut.measured.*` tells you what
was actually scored.

> **Why not omit `gamut` entirely when everything is in gamut?** It would save
> three lines per call, which is real across a few hundred tokens. But
> "absent means fine" is the exact signalling pattern that produced [#9].
> An explicit `false` costs little and teaches the field exists.

### Refusal  🔶 reason text changing

`--gamut-map none` with `--type okca` exits **2** with an explanation, rather
than silently measuring something else:

```
Error: --gamut-map none cannot be used with --type okca.
OKCA's guarantee is established across the sRGB gamut; outside it the
result is unvalidated extrapolation. Use --gamut-map clip or css, or
--type wcag2 / deltaE, which are defined continuously.
```

The shipped build gives a *representation* reason ("hex cannot represent…"),
which is wrong — okca accepts `oklch()` strings directly. The real limit is the
algorithm's **validity domain**, which is also the limit that matters for wider
gamuts later.

For an agent, refusing is the point: the alternative is silently recording a
number for a color it never asked about.

## 4. `find`

```
klar find <base-color> <reference-color> --target <n> [options]
```

| Flag | Default | Description |
|---|---|---|
| `--target <n>` | *(required)* | Target contrast |
| `-t, --type <type>` | `okca` | Algorithm |
| `--tolerance <n>` | `0.5` | Acceptable overshoot above target |
| `--axis <list>` | `lightness,chroma` | Which axes may move ⬜ |
| `-g, --gamut <space>` | `srgb` | Target gamut ⬜ |
| `--gamut-map <method>` | `clip` | Out-of-gamut resolution ⬜ |
| `--json` / `-q, --quiet` | | Output mode |

### Behavior — gamut first, then lightness, then chroma  ⬜ proposed

Today `find` moves lightness only, at the reference color's authored chroma.
When that chroma puts the color outside the gamut at *every* lightness, nothing
is reachable, so it returns the input unchanged and exits 1 — on exactly the
colors that gamut-aware `contrast` now flags.

The end state:

1. **Bring the color into the target gamut** by reducing chroma the minimum
   amount necessary. Lightness and hue hold.
2. **Search lightness** for the target, as today.
3. **If lightness exhausts, reduce chroma further**, minimally, and continue.

Gamut first, rather than lightness first, because it makes answers **nest**:
the sRGB answer is contained in the P3 answer is contained in Rec.2020. An
agent can then ask the same question per space and ship conditional tokens.
Lightness-first can land on a color that is still outside the gamut but happens
to reach the target *once clipped* — an answer that is only true for the space
it was clipped against, and silently stops being true on a wider display.

Chroma is reduced by the minimum that reaches the target, never more. Saturation
is brand intent, and this is a design-token tool.

Colors already inside the target gamut are unaffected: step 1 is a no-op and
the result is identical to today.

```bash
# Today — the axis that fixes this is never tried
klar find "oklch(1 0 0)" "oklch(0.79 0.22 25)" --target 6 -q
# oklch(0.79 0.22 25)          exit 1, unchanged

# End state (illustrative)
klar find "oklch(1 0 0)" "oklch(0.79 0.22 25)" --target 6 -q
# oklch(0.79 0.13 25)          exit 0
```

The chroma relationship this exploits, measured on the current branch:

| C at `oklch(0.79 C 25)` | painted | OKCA on `#070e16` |
|---|---|---|
| 0.22 | `#ff746f` | 4.0 |
| 0.15 | `#ff9189` | 5.9 |
| 0.12 | `#fe9b93` | 6.9 |
| 0.10 | `#f4a19a` | 7.5 |

### `--json`  ⬜ proposed additions

```jsonc
{
  "adjustedColor": "#f4a19a",
  "actualContrast": 7.5,
  "iterations": 14,
  "success": true,
  "reason": "ok",
  "axesAdjusted": ["chroma", "lightness"],
  "deltaE": 12,
  "oklch": { "l": 0.79, "c": 0.10, "h": 25 },
  "gamut": { "space": "srgb", "map": "clip", "outOfGamut": true },
  "message": "Reduced chroma 0.22 → 0.10 to reach srgb, then held lightness."
}
```

Three additions, all agent-facing:

**`reason`** — a machine-readable enum, so nothing has to parse prose:

| Value | Meaning |
|---|---|
| `ok` | Target met |
| `lightness-exhausted` | `--axis lightness` only; the lightness range ran out |
| `chroma-exhausted` | Chroma reached 0 (achromatic) and the target is still unmet |
| `unreachable` | Target exceeds what any color can reach against this base |

`message` stays, but becomes **human-only**. It is not an API and should not be
parsed. Today it is the only place the "lightness only" limitation appears,
which means automations regex an English sentence that any rewording breaks —
the same failure class as [#9], pre-staged.

**`axesAdjusted`** — an automation that assumed `find` only moves lightness
needs that assumption to break visibly, not silently. This is the breaking part
of the change, and it should be readable in the payload.

**`deltaE`** — perceptual drift from the reference color. Chroma reduction makes
drift matter more, and the playbook currently teaches a *separate*
`klar contrast --type deltaE` call to measure it. Folding it in saves one
invocation per token.

### `--axis`  ⬜ proposed

`--axis lightness` restores the 2.x behavior exactly, for anyone whose pipeline
depends on hue *and* saturation being preserved. `--axis chroma` moves chroma
only. Default is both.

## 5. `lightness` and `variants`  ⬜ proposed

Both gain `-g, --gamut <space>` and neither gains `--gamut-map`. They use gamut
to decide **which colors exist**, not what a color becomes — filtering, not
mapping.

```bash
klar lightness "oklch(0.5 0.22 25)" --gamut srgb    # L range available in sRGB
```

## 6. 8-bit quantization  ⬜ proposed

`--gamut-map clip` will quantize to the target space's bit depth (8 for sRGB).
This gives a property agents can rely on:

```
contrast X Y  ==  contrast <hex of X> <hex of Y>          for all X, Y under clip
```

That holds for `okca` today and not for `wcag2`/`deltaE`, which is a small
version of the same incoherence [#9] is about. klar's default algorithm has
always been 8-bit, since okca resolves through hex.

Bit depth is a property of the **gamut definition**, not of `clip` — P3 is
typically 10-bit, Rec.2020 12-bit. Hardcoding 8 would bake in an sRGB assumption
that has to be unpicked later.

**This is the one change that affects in-gamut colors**, by at most a rounding
step. `--gamut-map none` remains available for continuous precision.

## 7. Playbook guidance (agent-facing)

The additions to `AGENT_PLAYBOOK.md`, in the voice it uses.

### Gate vs. audit — pick the right output mode

The playbook currently teaches `-q` for everything. These are different jobs:

| Job | Mode | Why |
|---|---|---|
| **Gate** — "does this pass?" | `-q` + `$?` | One float, one exit code. Cheapest possible check. |
| **Audit** — "why, and what do I do?" | `--json` | You need `gamut.outOfGamut`, `reason`, `axesAdjusted`. |

Every byte of output is a token, paid on every call. Don't reach for `--json`
in a loop that only needs pass/fail; don't use `-q` when the next action depends
on *why* something failed.

### A failing token may be out of gamut, not too dark

If `contrast` fails and the color is authored in OKLCH, check
`gamut.outOfGamut` before adjusting anything. An out-of-gamut color is not too
dark or too light — it is **too saturated to be displayed**, and the display is
already showing a duller version. Reducing chroma raises real contrast while
holding lightness and hue.

`find` handles this now. Under 2.x it did not, which is why the playbook used to
carry a manual chroma sweep.

### Read `reason`, never `message`

```bash
REASON=$(klar find "$BG" "$FG" --target 4.5 --json | jq -r '.reason')
case "$REASON" in
  ok)                  ;;   # done
  chroma-exhausted)    ;;   # even neutral doesn't reach it — change lightness strategy
  unreachable)         ;;   # wrong base color; this pairing can't work
esac
```

`message` is prose for humans and its wording is not stable.

### Refusals are information

Exit 2 means klar declined rather than guessed — the algorithm was asked for a
number outside the domain where it is valid. Don't retry with different
flags to make it go away; the refusal is the answer.

## 8. Deliberately not in this release

| Item | Why |
|---|---|
| `--gamut p3` / `rec2020` | **Blocked upstream.** OKCA's chroma weighting saturates above a threshold: `oklch(0.79 0.22 25)` and `oklch(0.79 0.45 25)` both score 5.9 against `#070e16`. Inside sRGB the cap sits near the gamut boundary and this is invisible. In P3 it would flatten real differences into one number. Needs answering in okca before any wide-gamut flag means anything. |
| Plugin gamut declaration | `calculate(colorOne, colorTwo)` gives plugins two strings with no way to declare what they accept or where their algorithm is valid. Safe while everything is sRGB; unsafe the moment it isn't. Belongs in a plugin-interface major. |
| Bulk / multi-color audit | Real gap for developers with large token sets — today they script it. A genuine feature, not a rider on this one. |
| Joint (L,C) optimization in `find` | More optimal, less predictable. An agent has to justify the change it made; "reduced chroma to 0.10, the least that reaches 4.5" is explainable in a commit message, and an optimizer's pick isn't. |

## 9. Open questions for review

1. **Is `--gamut-map` worth the surface area now**, given `--gamut` accepts only
   `srgb`? The alternative is one flag today and a rename later, when it will
   break automations rather than just being new.
2. **Should `--axis lightness` be the default** for one release, with
   `lightness,chroma` opt-in, to soften the break for existing `find`
   automations? My inclination is no — it leaves the primary user with the
   broken behavior by default, which is the [#9] mistake again.
3. **Does the stderr note risk being noise** in agent harnesses that surface
   stderr prominently, given it fires on every out-of-gamut call in a loop?
